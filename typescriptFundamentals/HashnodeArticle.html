Learning Log: TypeScript

Mastering TypeScript OOP: An Architect's Log

Moving from "making code work" to "architecting systems." A journey through the pillars of Object-Oriented Programming.

The Shift to Structural Thinking

For a long time, my approach to coding was procedural. I wrote functions, I looped through arrays, and if the output was correct, I was happy. But as my projects grew, I hit a wall. My "simple" scripts were becoming a tangled web of global variables and repetitive logic.

The transition to Object-Oriented Programming (OOP) wasn't just about learning new keywords like class or interface; it was about shifting my mindset. I stopped asking "What happens next?" and started asking "What is this thing, and what are its responsibilities?"

The Blueprint Era: Classes & Constructors

My first encounter with Classes felt like discovering a factory. Instead of manually crafting every object, I could create a blueprint.

The Pain Point I was creating multiple "Student" objects manually. Every time I added a new field (like email), I had to update every single object literal in my code. It was a maintenance nightmare.
The Breakthrough: The Constructor. Realizing that a class could automate initialization meant I only had to define the structure once.
Procedural Thinking "I need another student object with an ID, name, and email."
OOP Thinking "I need an instance of the Student blueprint." 
class Student {
    constructor(
        public readonly studentId: number,
        public name: string,
        public email?: string
    ) {}
}

const stu1 = new Student(101, "Saksham");

Building Walls: Access Modifiers

As I built more complex classes, I noticed a problem: any part of my code could reach inside my objects and change things they shouldn't. I could accidentally change a studentId, which should be immutable.

The Pain Point "Leakage." My internal class data was too exposed. I didn't have a way to protect critical properties from external interference.
The Breakthrough: Encapsulation. Using private and protected modifiers to hide the "guts" of the class and providing controlled access via Getters and Setters. 
class Student {
    private _name: string;

    constructor(name: string) { this._name = name; }

    // Controlled access via Getter
    get name(): string { return this._name; }

    // Controlled mutation via Setter
    set name(newName: string) {
        if (newName.length > 0) this._name = newName;
    }
}

The Family Tree: Inheritance & Polymorphism

Then came the realization that not all objects are unique. Some are specialized versions of others. A Car is a Vehicle. An ElectricCar is a Car.

The Pain Point Repeating the same start() and stop() methods across five different car classes. The code was bloated and hard to update.
The Breakthrough: The extends keyword. I could define common logic in a Parent class and only override the specific parts that changed in the Child class. 
                classDiagram
                    Vehicle <|-- Car
                    Car <|-- ElectricCar
                    class Vehicle {
                        +name: string
                        +start()
                    }
                    class Car {
                        +year: number
                        +start() // Overridden
                    }
                    class ElectricCar {
                        +batteryCapacity: number
                        +start() // Overridden
                    }

The most "magical" moment was **Polymorphism**. The ability to treat an ElectricCar as a generic Vehicle meant I could create a list of different vehicles and call .start() on all of them without caring about their specific type. The right version of the method always ran.

The Contract: Interfaces & Abstraction

Eventually, I asked: "What if I don't have a Parent class, but I want to guarantee that several different classes all have the same method?"

The Pain Point The "Interface vs. Abstract Class" dilemma. I struggled to understand when to use a blueprint for identity (Abstract Class) versus a blueprint for behavior (Interface).
The Breakthrough: Thinking of Interfaces as "Contracts." An interface doesn't care what you are; it only cares what you can do.
Abstract Class "I am a type of Appliance (Identity)."
Interface "I can make a sound (Capability)." 
interface SoundMaker {
    sound(): void;
}

class Dog implements SoundMaker {
    sound() { console.log("Woof!"); }
}

The Swiss Army Knife: Overloading & Tuples

To wrap up my fundamentals, I dove into the "edge cases" that make TypeScript incredibly flexible: Function Overloading and Tuples.

Overloading felt like a puzzle. Writing one implementation that satisfied three different signatures required a deep dive into Type Guarding. Tuples, on the other hand, gave me the precision of an array with the safety of a fixed structure.

The Final Assembly: Modules

The final step was organization. I moved my logic out of single, massive files and into Modules. Using export and import transformed my project from a collection of scripts into a professional codebase.
